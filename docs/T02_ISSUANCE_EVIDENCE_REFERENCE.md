# T-02.2C.2B.2B — reference issuance and approval evidence

Non-production reference only, stacked on PR #18 (CI #259 passed both jobs; committed first admission, late approval expiry, positive termination wait, zero sessions and reconnect denial verified in PG16.16). Existing migrations, application source, R-26, scanner and required Python job retained. New engineering reference uses cryptography Ed25519 verification (development dependency only).

Approval signing binds the exact deployment, role, OID, generation, tenant, business unit, approval ID, change reference, both subjects, and validity window, with domain-separated canonical ASCII JSON and signer identity. Verification requires exact expected tuple, expected SHA-256 evidence digest, authoritative time, two distinct enrolled subjects and public keys, and both valid signatures. The registry's digest can bind this representation; database integration and authorization of actual human signers remain unimplemented. The reference assumes independently trusted key enrolment and time; two keys do not themselves establish two independent humans. No private keys are stored by the verifier. Tests use ephemeral keys. Initial role names use a deliberately narrower ASCII alphanumeric/underscore subset (1–63 bytes). UUIDs must be canonical lowercase and timestamps integer epoch seconds.

The local SQLite ledger preserves reservations even before database role creation, with unique deployment/name and global generation, append-only triggers, deterministic chained hashes, explicit bootstrap, and mode=rw thereafter. Every operation compares the entire scanned ledger against a supplied independently trusted checkpoint; mismatch or missing file denies. Reservation returns a candidate checkpoint, not a durable external anchor receipt. A separate trusted anchor must compare-and-append and confirm the new head before any role creation; require_reserved must receive the independently read anchor, never an untrusted caller's candidate. Crash after local append but before anchor advancement intentionally requires controlled reconciliation. The local database is not tamper-proof, replicated, externally anchored or independently backed up; its triggers do not defend against a privileged file/database administrator. The reference has no actual anchor adapter, remote authorization/key registry, durable two-human workflow, vault/network fence, or production admission integration. R-01/R-03 remain open. No production claim or merge authorized.

New reference tests cover signature verification, scope/OID tampering, digest mismatch, expiry, unknown signers, shared key, swapped signatures, role/generation reuse, wrong scope reservation, missing ledger, mutation denial and restore mismatch.
