# T-02 — PostgreSQL tenant isolation architecture

Status: proposed, documentation only; implementation and independent acceptance pending.
Baseline: R-26 0522c53560b4082b08a0fb379ca50f137253c054 (PR #11). Gate 0.1.2 remains unaccepted.

## Baseline and scope
The inspected architecture, security baseline, package metadata, composition root and tenant contracts establish a modular monolith, opaque identifiers, trusted adapter interfaces and a bounded static scanner. No production database implementation is established by this evidence. Main-to-baseline comparison reports 145 commits ahead, zero behind and 16 changed files; it is not a complete tree inventory. Preserve the accepted stack and do not merge without explicit authorization. The original roadmap places security foundation at Gate 0.4; T-02 is proposed prerequisite work for the broader Gate 0.1.2 acceptance, subject to explicit governance reconciliation before implementation.

## Decisions proposed
- PostgreSQL 16 or 17, Psycopg 3, versioned SQL migrations; supported versions verified in real database CI.
- Preserve opaque case-sensitive 1–128 character identifiers and existing validation semantics; use text with explicit constraints and deterministic collation, not implicit UUID conversion.
- Tenant registry and business-unit registry with composite tenant/business-unit keys. Every scoped operational row carries both identifiers; composite foreign keys include scope to prevent cross-scope references.
- Separate non-login owner, migration identity, restricted runtime identity and narrowly scoped membership lookup identity. Runtime must not own tables, inherit owner privileges, have BYPASSRLS, superuser, role administration, TRUNCATE or DDL privileges. No broad PUBLIC grants. Administrative roles remain outside the runtime threat boundary.
- Enable and FORCE RLS on scoped tables. Explicit SELECT, INSERT, UPDATE, DELETE policies with USING and WITH CHECK as applicable; no permissive broad policy. Missing, empty or malformed context denies access. Scope changes through UPDATE are forbidden.
- Bind subject, tenant and business unit only from trusted adapter output, in an explicit transaction using parameterized transaction-local settings. Never derive context from raw request fields. No session-level scope or autocommit data access. Rollback on failure, reset/verify pooled connections before reuse, discard connections on cleanup failure.
- Custom PostgreSQL settings are not unforgeable credentials: the runtime SQL identity can change them. RLS with these settings protects against omitted filters and accidental scope mistakes, not arbitrary SQL execution or compromised runtime identity. Restrict SQL execution to reviewed parameterized repository operations; no user SQL, no raw connection exposure. Evaluate stronger database-authenticated scope binding before claiming resistance to compromised runtime SQL.
- Membership lookup must be server-authoritative, restricted and separately authorized; no circular dependency on an unverified tenant scope. T-03 defines identity validation and membership revocation semantics; T-04 implements transaction/pool boundary. T-02 test harness must not be presented as production authentication.
- No SECURITY DEFINER functions by default; any exception requires explicit grants, fixed safe search_path, qualified objects and independent review. Avoid owner-executed views bypassing RLS; test effective runtime privileges and policy catalog.
- Customer-controlled deployment, offline signed licensing separate from authorization. No customer credentials or live carrier integration.

## Acceptance matrix
- Valid scope: allowed CRUD within tenant and business unit.
- Different tenant and same-tenant different unit: reads invisible; inserts and scope-changing updates rejected; update/delete cannot affect foreign rows.
- Missing/empty/malformed scope: no data access; writes rejected.
- Composite FK rejects cross-scope references; test uniqueness and error leakage boundaries.
- Runtime cannot disable RLS, alter policy, assume owner, truncate, or bypass through inherited roles; verify catalog and effective privileges.
- Transaction rollback, commit, pool reuse and concurrent requests: no residual scope; full pool tests in T-04.
- Test membership revocation and unauthorized identity in T-03/T-05; background jobs, exports, caches and object storage remain separate work packages.
- Document residual risks including privileged DB administrators, arbitrary runtime SQL, side channels and deployment misconfiguration.

## T-02.1 design refinement — proposed for independent review

This section supersedes the provisional shared runtime role/custom-setting scope binding above. It does not grant implementation authorization or owner approval of the roadmap.

### A01 — database-authenticated tenant and business-unit binding
Use one restricted PostgreSQL login identity per tenant/business-unit pair for the first implementation. The database authenticates the login directly. A protected binding registry maps its authenticated session_user to exactly one tenant/business-unit pair. Use FORCE RLS on the registry, read-only access to the login's own mapping, no runtime registry writes, and fail closed for missing or disabled mappings. Operational policies require the bound pair and matching well-formed transaction-local scope; changing custom settings cannot widen the database login's permitted pair. The subject setting remains trusted application context, not database-authenticated end-user proof. No cross-scope login membership, arbitrary role assumption, shared privileged connection or user SQL. A trusted connection broker selects the pool only after verified identity/membership and verifies session_user and binding before work. Pool keys include deployment, database and scoped identity. A compromised broker/application with access to multiple credentials, privileged DBA, and malicious same-scope SQL remain outside this isolation guarantee. Evaluate credential/pool cardinality and operating cost before scale-out. Do not advertise end-user-level database authentication.
Provisioning must prevent stale mappings and role-name reuse: opaque unique login names, disable binding and revoke login, drain/terminate affected sessions, remove binding and retire credential on deprovisioning. Restore/rotation procedures must revalidate all identity bindings. No raw customer IDs in role names.

### A02 — proposed effective privilege matrix
- Bootstrap administrator: creates roles/database, not an application credential.
- Migration login: tightly controlled owner assumption only for reviewed migrations; no application pooling.
- Object owner: NOLOGIN; owns schemas, tables and policies; no application membership.
- Scoped runtime login: restricted operational CRUD (column-specific UPDATE excluding scope keys); own binding read only. NOSUPERUSER NOBYPASSRLS NOCREATEROLE NOCREATEDB NOREPLICATION. No ability to assume another scope, membership reader, migration or owner.
- Membership lookup login: read only on separately protected authoritative membership path; no operational data or registry modification. Restrict access to trusted provider; lookup cannot establish end-user authentication by itself.
- Registry provisioner: separately controlled lifecycle operations; not a runtime login.
- PUBLIC: explicitly revoke unnecessary database CONNECT/TEMP, schema CREATE/USAGE, and object privileges; grant only required rights, set safe schema-qualified access and creator-specific default privileges. No blanket grants to existing or future tables. Test effective grants and transitive role memberships using actual logins. Any shared NOLOGIN privilege role must not allow changing login scope.

### A03/A04 — integrity and revocation
Use C-collated opaque identifiers with 1–128 ASCII characters matching the Python contract. Include tenant and business unit in operational primary, unique and foreign keys; prevent scope updates with column privileges. Registry writes require separate provisioning. PostgreSQL referential-integrity checks can bypass RLS; avoid global operational uniqueness and sanitize constraint diagnostics. Do not claim elimination of all timing/error side channels.
The policy must require an active database binding plus syntactically valid matching transaction context, including subject. T-03 must define authoritative membership validation, recheck at transaction start, revocation handling and maximum in-flight authorization lifetime. A transaction already running under a prior snapshot is not instantly revoked. T-04 must implement scoped pool routing, cleanup and cancellation/discard on failure. No application use until T-03/T-04 are verified.

### A05 — required evidence
First target PostgreSQL 16; 17 is unqualified until separately tested. Test direct authentication as each scope login, cross-scope setting changes, SET ROLE/session-authorization escalation denial, missing/disabled mapping, cross-scope CRUD, column privileges, default privileges, RLS catalog and constraint behaviour. Require a real database in integration CI; no silent skips. Verify migrations from clean database, rollback and upgrade. Preserve the existing R-26 checks. Test subject forgery within a scope as an explicit limitation, not a passed end-user authentication control.

### A06 — governance
Full recursive inventory, branch protection and required checks remain unverified. Proposed reconciliation: runtime isolation is a prerequisite for Gate 0.1.2; Gate 0.4 retains broader hardening and revalidation. Owner approval and independent design acceptance remain pending; ROADMAP.md is unchanged. No implementation or merge authority.

## T-02.1A — normative proposed specification (review LOGISTICSOS-T02-ISR-001)

Status: design remediation submitted for review; not implemented, tested or approved. This section supersedes earlier conflicting design language. F01–F06 are addressed at specification level only; F07 owner approval and F08 external evidence remain open. No production migrations or runtime integration authorized. PostgreSQL 16 is the first qualification target.

### F01: authenticated registry and lifecycle

Protected schema security; operational schema ops; registry and provisioning ledger owned by non-login owner. Scope binding relation security.scope_binding has role_name name PRIMARY KEY, role_oid oid NOT NULL UNIQUE, tenant_id and business_unit_id constrained text NOT NULL, active boolean NOT NULL DEFAULT false, generation uuid NOT NULL UNIQUE, created_at timestamptz NOT NULL, disabled_at timestamptz nullable, composite FK to provisioned business unit. Partial UNIQUE (tenant_id,business_unit_id) WHERE active; disabled timestamp consistency check. Persistent security.role_retirement ledger contains every issued name and generation, never deleted, with issuance/retirement timestamps and cluster/deployment identity; no runtime access. No password in either relation. Provisioning uses fresh random opaque role name (ASCII, <=63 bytes) and generation, checks durable ledger under serialized administrative lock; no role-name reuse even after restore. OID is cluster-local and may be reused; OID check is defense in depth, not a durable generation proof. No untrusted role creator; privileged administrator bypass remains outside guarantee.

Registry predicate B: role_name = SESSION_USER AND active IS TRUE AND EXISTS (SELECT 1 FROM pg_catalog.pg_roles r WHERE r.rolname = SESSION_USER AND r.oid = scope_binding.role_oid AND r.rolcanlogin AND NOT r.rolsuper AND NOT r.rolbypassrls). Registry policies: ENABLE and FORCE RLS; one PERMISSIVE SELECT TO scoped_runtime USING (B), one RESTRICTIVE FOR ALL TO scoped_runtime USING (B) WITH CHECK (false). Grant scoped_runtime SELECT only on role_name, role_oid, tenant_id, business_unit_id, active; no write, generation/ledger access or registry DDL. Provisioner uses separate controlled administrative maintenance transaction with explicit reviewed administrative policies TO dedicated provisioner, not runtime; the restrictive registry policy applies only to scoped_runtime so authorized provisioning is possible. Runtime membership in provisioner prohibited. Provisioner has explicit SELECT/INSERT/UPDATE policies and narrowly scoped column grants; no deletion of tombstones. Operational access requires exactly one active mapping; uniqueness prevents ambiguity. Registry predicate reads system catalog only, never operational tables or membership store. Missing, inactive or mismatched OID produces no visible binding.

Lifecycle: offline administrator creates NOLOGIN role, writes inactive binding and permanent issuance ledger in same PostgreSQL transaction, grants vetted privileges, records audit; secret stored in customer vault and connection routing disabled until verified. Activate binding and LOGIN in controlled transaction after secret readiness; broker enables route only after real login/catalog verification. Rotation: deny new checkouts, drain/cancel and terminate old sessions, rotate vault/database credential, revalidate before reenable. Retirement: broker blocks scope; commit inactive binding and NOLOGIN, revoke CONNECT/grants as applicable, terminate all matching sessions and verify zero, retire secret, drop role only after dependent object check, retain disabled binding/tombstone. Role-name reuse forbidden. Audit actor, action, deployment, generation, OID and outcome, never secret. Partial failure leaves route disabled; reconciler quarantines inconsistencies. Restore or clone: deny all broker routes and runtime CONNECT before serving; reconcile ledger against independent durable backup, create fresh names/generations and OIDs, retire restored credentials, validate catalog and binding, then activate. If ledger unavailable, block activation. Test stale name/OID, same-name recreation with different OID, missing mapping, disabled binding and restored cluster mapping; do not rely on OID uniqueness across time/clusters.

### F02: normative operational policy template

For every scoped operational base table t, define S(t) = valid(subject) AND valid(tenant_setting) AND valid(unit_setting) AND t.tenant_id = tenant_setting AND t.business_unit_id = unit_setting AND EXISTS (SELECT 1 FROM security.scope_binding b WHERE b.tenant_id = t.tenant_id AND b.business_unit_id = t.business_unit_id AND b.role_name = SESSION_USER AND b.active IS TRUE). Settings are pg_catalog.current_setting('cephas.subject_id', true), 'cephas.tenant_id', 'cephas.business_unit_id'; valid means NOT NULL and exact identifier predicate F06; wrap entire predicate in COALESCE(...,false). Registry RLS independently enforces B. Qualify all schema/object references. No SECURITY DEFINER helper. No operational policy referencing operational table recursively. Set local context via parameterized set_config only inside explicit verified transaction. End-user subject remains application-trusted.

Every scoped table ENABLE and FORCE RLS. One RESTRICTIVE FOR ALL TO PUBLIC USING (S) WITH CHECK (S); four explicit PERMISSIVE policies TO scoped_runtime: SELECT USING (S), INSERT WITH CHECK (S), UPDATE USING (S) WITH CHECK (S), DELETE USING (S). No policy granting other roles operational access by default. Separate administrative maintenance procedure requires change approval; restrictive operational policy not weakened for convenience. Ordinary grants still required; UPDATE only allowed non-scope columns. A new permissive policy cannot widen scope while restrictive invariant applies. No access if permissive policy absent. Catalog allowlist compares relrowsecurity/relforcerowsecurity, owner, ACLs, policy commands, role OIDs, permissiveness and normalized pg_get_expr expressions against reviewed manifest; fail on unknown relations, partitions, policy changes or grants. No views, functions with privileged execution, alternate schemas, foreign tables, or direct partition grants in T-02; introduce only via reviewed change and negative tests. Test adding temporary permissive TRUE policy as privileged fixture: foreign scope remains denied; catalog drift check separately fails. Remove fixture transactionally. Test row_security=off errors rather than bypass.

### F03: broker and capacity envelope (proposed initial limits, not measured)

Single deployment/database, <=100 active scope pairs, <=2 broker replicas total (including failover overlap); each replica <=40 physical connections total (active + idle + opening), <=2 per scope, <=20 idle total, lazy pools and zero minimum connections; global broker budget 80 physical connections. Database max_connections proposed 120, including 20 non-broker ordinary operational/admin connections and 20 reserve/headroom; verify reserved connection settings and resource use on target installation. Per-login CONNECTION LIMIT 4 is defense in depth, not a precise global admission controller. Use broker-side atomic admission, bounded queue 100 requests/replica, checkout <=2 seconds, idle eviction <=60 seconds; reject overload without fallback to shared privileged role. Failover must fence old replica before replacement admission or consume its existing quota; no third simultaneous replica. External transaction pooler unsupported until proven to preserve direct authenticated session identity and pool separation; no forced-user mode. Load-test 100 pairs, skew, churn, exhausted pool and database outage; expand only with approved capacity evidence. These limits are initial design choices, not throughput claims.

Pool identity = deployment ID, database endpoint/identity, authenticated role name, generation, credential version. Only verified TenantScope from trusted adapter routes via deployment-owned mapping; request fields cannot pick database role, DSN or secret path. Broker validates TLS server identity, database identity, SESSION_USER and active mapping before each checkout. Customer vault holds scoped credentials, accessed only by broker service identity, deployment-scoped allowlist, no broad listing or application credential exposure; use separate admin/membership secret namespaces. No secrets in logs/DSNs returned to request code. Broker compromised may expose up to all 100 pairs of that deployment; not a single-scope guarantee. Isolate deployments, revoke broker vault access, block routing, retire/rotate all affected scoped credentials, terminate sessions, audit and requalify. T-04 implements broker, cancellation, cleanup and routing; no claim of implemented isolation.

### F04: T-03 membership contract and T-04 transaction dependency

Proposed identity provider: customer-configured OIDC issuer with pinned issuer/audience, permitted algorithms and verified signature, expiry/not-before and subject; stable local subject mapping by issuer + subject, never email or arbitrary client claim. Authoritative membership store: customer-controlled PostgreSQL security membership relation, unique (subject_id,tenant_id,business_unit_id), active state and monotonically incremented revision, separate least-privilege lookup login; protected administration path only, audit changes. Runtime scope logins cannot read raw membership records. Verify authenticated identity and exact active membership on every request and again immediately before transaction starts; no positive membership caching. Reject unavailable source, expired credential, inactive/mismatched membership or ambiguous identity. Revocation commits increment revision, invalidate pending decisions, notify broker and cancel affected in-flight work; lost notification cannot extend proposed authorization lifetime. Maximum 30 seconds from final authoritative check through transaction completion, shorter if credential expires; no checkout reuse of old decision. PostgreSQL 16 lacks a general transaction_timeout: enforce independent trusted broker watchdog with bounded statement and idle-in-transaction timeout, cancel then terminate/discard when deadline reached; recheck deadline before commit. Statement timeout alone not sufficient, and arbitrary malicious SQL can change session settings. Document residual race: commits already in flight or completed before cancellation may succeed; bounded guarantee requires measured cancellation and fail-closed operational controls, not instant revocation. No long-running user transaction; split operations and reauthorize each chunk. Queued jobs carry immutable scope/subject/job ID, not authorization token; reauthenticate trusted worker and revalidate subject/service principal membership at execution and each chunk; revoked jobs denied. Checked-out connections affected by revocation quarantined and discarded; idle connections hold no subject decision and require fresh check. Audit identity rejection, membership change, scope denial, cancellation and expiry without credentials. T-03/T-04 implementation and tests mandatory for Gate 0.1.2; this contract is not proof of end-user auth or revocation.

### F05: role and grant matrix

All non-bootstrap identities NOSUPERUSER NOBYPASSRLS NOCREATEDB NOCREATEROLE NOREPLICATION NOINHERIT; LOGIN only migration, provisioner, membership lookup and scoped runtime. NOLOGIN owner and scoped_runtime group. Bootstrap customer DBA is privileged external actor, not pooled; only DBA administers roles, role grants, provisioner and secret rotation; two-person approval proposed for privileged changes. Migration login -> owner WITH INHERIT FALSE, SET TRUE, ADMIN FALSE; sole allowed owner assumption, explicit reviewed SET ROLE then RESET ROLE. Runtime login -> scoped_runtime WITH INHERIT TRUE, SET FALSE, ADMIN FALSE; no other memberships, group has none. Membership and provisioner roles have no memberships; provisioner receives narrowly explicit registry rights and cannot create roles. No owner grant options to migration beyond controlled owner assumption; owner has no role-admin privilege. DBA creates roles, not provisioner. All runtime/login roles nonowners. Revoke PUBLIC CONNECT/TEMP on dedicated database, CREATE/USAGE on application schemas and public schema as appropriate; grant explicit CONNECT/schema USAGE and object-specific privileges only. For every allowed creator (owner and any approved migration creator), revoke default PUBLIC EXECUTE on functions and unnecessary default privileges at global level and audit schema-specific defaults; enforce owner-only object creation via migration. No public object creation, broad sequence grants, TRUNCATE, REFERENCES, TRIGGER or GRANT OPTION for runtime. Catalog assert attributes, transitive pg_auth_members options, ownership, ACLs, pg_default_acl, pg_has_role MEMBER/USAGE/SET and has_*_privilege; actual login negative tests for SET ROLE, SET SESSION AUTHORIZATION, DDL, role grant, RLS changes, registry modification, alternate object access. Test future object defaults using each permitted creator. Privileged owner/DBA remains trusted; migration credentials never at runtime.

### F06: exact identifiers and composite integrity

Use NOT NULL text COLLATE "C" and CHECK (char_length(id) BETWEEN 1 AND 128 AND id ~ '^[A-Za-z0-9]' AND id !~ '[^A-Za-z0-9._:-]') for subject, tenant, unit and operational identifiers. This is equivalent to Python fullmatch [A-Za-z0-9][A-Za-z0-9._:-]{0,127}, with explicit length; tests include trailing newline, whitespace, Unicode, leading punctuation, empty, 128/129 characters. Apply predicate to context settings too. Tenant registry PK tenant_id; unit registry PK (tenant_id,business_unit_id), FK tenant_id. Every operational PK/unique/FK and association key contains complete tenant+unit scope; example scoped entity PK (tenant_id,business_unit_id,entity_id), child FK same tuple, association FK both endpoints with common scope. No global operational uniqueness, no arbitrary client-selected upsert conflict targets, no scope-column update privileges. FK/unique checks may bypass RLS; restrict operations to verified scope, normalize error responses, avoid exposing constraint names or foreign identifiers, test same entity IDs across scopes, cross-scope association and upsert, no scope move. Registry metadata privileged; timing/error side channels not eliminated.
